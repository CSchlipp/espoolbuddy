# Development / repository layout

For anyone poking at the code rather than just building the hardware:

```
espoolbuddy/
├── espoolbuddy_console.yaml            # Console entry point (WT32-SC01 Plus: display + NFC + speaker)
├── espoolbuddy_console_pandatouch.yaml # Alternate console entry point (Panda Touch: display + NFC via I2C)
├── espoolbuddy_console_scale.yaml      # Alternate console entry point (WT32-SC01 Plus + NAU7802, SpoolmanScale wiring)
├── espoolbuddy_console_lite.yaml       # Lite console entry point (Waveshare 1.47": display + NFC via I2C, Lite UI)
├── espoolbuddy_scale.yaml              # Scale entry point (HX711 + NFC, headless)
├── secrets.yaml.example               # Template — copy to secrets.yaml (git-ignored)
├── espoolbuddy/                       # Packages the entry points include
│   ├── bundles/                       #   The one file each entry point lists in packages: files:
│   │   ├── console_full.yaml          #     Console bundle: version + app + assets + lvgl (tabbed UI)
│   │   ├── console_lite.yaml          #     Lite bundle: version + app_lite + assets + lvgl_lite
│   │   └── scale.yaml                 #     Scale bundle: version + app_scale
│   ├── version.yaml                   #   Single SemVer version shared by every device variant
│   ├── app.yaml                       #   UI logic, sleep state machine, NFC/scale wiring, sensors
│   ├── app_scale.yaml                 #   Scale logic: status LED
│   ├── lvgl.yaml                      #   LVGL screen/widget layout (resolution-independent)
│   ├── app_lite.yaml                  #   Lite UI logic (one refresh script, sleep, Quick Weight)
│   ├── lvgl_lite.yaml                 #   Lite UI widget tree (172x320 portrait, single screen)
│   ├── assets.yaml                    #   Fonts (MDI webfont) and image declarations
│   ├── label_printer_m220.yaml        #   Optional package: Phomemo M220 label printer
│   ├── images/                        #   PNG icons (spool fill/shine/empty, AMS icons)
│                                      #   downloaded from GitHub at compile time, see below
│   └── lvgl/                          #   Per-tab LVGL definitions (AMS tab, NFC tab)
├── components/                        # Shared ESPHome external_components
│   ├── bambuddy_api/                  #   HTTP client/server + Bambuddy API protocol (C++)
│   ├── label_printer/                 #   Label printing core: job, PNG decode, driver/transport interfaces
│   ├── label_printer_ble/             #   Bluetooth LE transport for label printers
│   ├── label_printer_file/            #   Simulator's label printer: writes a PBM image
│   ├── label_printer_phomemo/         #   Phomemo M series protocol (a label printer driver)
│   └── bambuddy_nfc/                  #   PN532 driver + Bambu MIFARE key derivation (C++)
│       ├── bambuddy_nfc.*             #     Bus-independent reader logic (abstract base class)
│       ├── bambuddy_nfc_spi.*         #     SPI transport (`interface: spi`, default)
│       └── bambuddy_nfc_i2c.*         #     I2C transport (`interface: i2c`)
├── host/                              # Desktop simulator of the console UIs (see below)
│   ├── espoolbuddy_console_host.yaml  #   Host-platform entry point, full UI (SDL window)
│   ├── espoolbuddy_console_host_labels.yaml # The same with a label printer that writes to a file
│   ├── espoolbuddy_console_lite_host.yaml # Host-platform entry point, Lite UI at 172x320
│   ├── host_common.yaml               #   Shared by both: mock, SDL display/touch, simulate buttons
│   ├── bambuddy_api_mock.cpp          #   Mock backend with demo data, replaces bambuddy_api.cpp
│   ├── docs_screenshots.yaml          #   Scripted simulator run that snapshots each documented screen
│   ├── docs_screenshots_lite.yaml     #   Same for the Lite UI
│   └── update_screenshots.py          #   Regenerates docs/images/ui/ from both screenshot runs
├── docs/                              # This documentation, plus wiring/architecture diagrams
│   └── images/ui/{full,lite}/         #   UI screenshots per UI, generated by host/update_screenshots.py
└── .github/workflows/                 # CI: compiles every config against the latest ESPHome release
```

`bambuddy_nfc` is one component with two host interfaces. Everything above
the byte level — PN532 framing, tag detection, the Bambu HKDF read with its
retries, NTAG write, NDEF detection and the polling task — lives in the
abstract `BambuddyNFCComponent`. `BambuddyNFCSPIComponent` and
`BambuddyNFCI2CComponent` only implement a handful of transport hooks
(wake-up, status byte, raw read, frame write, response read). The YAML
`interface:` key picks one, and only that one is compiled (guarded by
`USE_BAMBUDDY_NFC_SPI` / `USE_BAMBUDDY_NFC_I2C`).

The two components talk in both directions — the reader reports scans to
`bambuddy_api`, and `bambuddy_api` drives the reader's sleep behaviour and
reports it to the backend — but the YAML needs only one link: `bambuddy_nfc`'s
`api_id`. Its code generation calls `set_api_component()` on itself and
`set_nfc_component()` on the API component, so a configured reader is always
wired up completely.

**Label printing is three components.** `label_printer` holds the print job
(fetch the PNG from Bambuddy, decode it into a 1-bit raster placed in the
print row, send it, wait for the result), the result codes and the button
text; it's all the UI talks to (`label_printer::global_label_printer`, under
`USE_LABEL_PRINTER`). A *driver* is a printer's protocol: it describes the
printer as data (resolution, head width, write size and pacing, its Bluetooth
profile) and turns the raster into the printer's bytes, a chunk at a time
straight from the raster. A *transport* gets those bytes to the printer and
owns flow control: `label_printer_ble` connects through a `ble_client`,
switches Bluetooth on only for a print, and finds and remembers the printer
by the driver's advertisement rule. `label_printer_phomemo` is the only
driver so far. A new printer model is a driver, a new way to reach one (USB,
network) is a transport, and neither needs a change to the core or the UI.

`espoolbuddy_console.yaml`, `espoolbuddy_console_pandatouch.yaml` and
`espoolbuddy_console_scale.yaml` pull in the same
`espoolbuddy/bundles/console_full.yaml` bundle — the UI and app logic are
written once and shared; only hardware pinout/wiring differs between the
files. `espoolbuddy_console_lite.yaml` pulls in
`bundles/console_lite.yaml` instead: a separate, much smaller widget tree
(`lvgl_lite.yaml`) and logic file (`app_lite.yaml`) on top of the same
`bambuddy_api` component. The two UIs share no widget ids, so a console
includes exactly one bundle. `espoolbuddy_scale.yaml` pulls in
`bundles/scale.yaml` the same way.

A bundle is a package file with nested `packages:` that `!include` its
parts, plus the wiring every board of its kind needs (boot hooks, the
Tare/Restart buttons, the backlight wake script; for the scale, the status
LED). Entry points keep only hardware and settings.
Configs copied before the bundles existed list the parts one by one and
carry that wiring inline, so it stays out of `app.yaml` to avoid duplicates.
CI builds `.github/legacy/espoolbuddy_console.yaml`, a frozen copy of such a
config, to prove they still work.

`components/` is pulled by all five entry-point YAMLs via
`external_components: source: git ...` pointed at this repo's own `main`
branch, so each YAML also works as a standalone copy-paste example. The PNGs
in `espoolbuddy/images/` are fetched the same way: `assets.yaml` builds their
URLs from an `espoolbuddy_images` substitution pinned to the same
`${espoolbuddy_ref}`, and ESPHome downloads and caches them at compile time
(under `.esphome/image/`) rather than reading them off disk. When developing
locally, CI rewrites the components, packages and image sources to the local
checkout before compiling — see `.github/scripts/use_local_components.py` if
you're doing the same.

No other build tooling, no lint step, no unit tests — the closest thing to
a test suite is a full firmware compile of every config, both locally
(`esphome compile <file>`) and in CI on every push/PR.

**Desktop simulator.** `host/espoolbuddy_console_host.yaml` builds the
console UI for ESPHome's `host` platform, so it runs as a normal program in
an SDL window and the mouse acts as the touchscreen. UI changes can be tried
without flashing hardware:

```
esphome run host/espoolbuddy_console_host.yaml        # full UI
esphome run host/espoolbuddy_console_lite_host.yaml   # Lite UI, 172x320
```

This needs the SDL2 development files (`sudo apt install libsdl2-dev`, or
`brew install sdl2`). It uses the local checkout for everything (components,
packages and images). Change `screen_width`/`screen_height` in that file, or
pass `-s screen_width 800 -s screen_height 480`, to see the Panda Touch
layout. Press `s` in the window to save a screenshot to
`host/.esphome/snapshots/`.

**Doc screenshots.** The UI screenshots in `docs/images/ui/full/` and
`docs/images/ui/lite/` are generated,
not taken by hand. After a UI change, regenerate them with the Python that
has ESPHome installed:

```
python host/update_screenshots.py
```

It compiles `host/docs_screenshots.yaml` at 480×320 and 800×480 and
`host/docs_screenshots_lite.yaml` at 172×320, and runs each
off-screen (SDL's dummy video driver, so no display is needed). The run
drives the UI through each documented screen with simulated taps and NFC
scans, saves a snapshot of each, and the script writes them to
`docs/images/ui/full/` and `docs/images/ui/lite/` as PNGs. Pass resolutions
to render only those, e.g. `python host/update_screenshots.py 172x320` for
just the Lite set.

Screens both UIs have are listed in `SHARED` in `update_screenshots.py`: both
walkthroughs take them under the same name, with the same steps and demo
data, so `full/<name>.png` and `lite/<name>.png` always show the same
situation. `docs/usage.md` embeds the full version of each and
`docs/console-lite.md` the Lite version. To document a new shared screen,
add the step to **both** `docs_screenshots*.yaml` files, its name to
`SHARED`, and the image to both pages. A screen only one UI has goes into
`FULL_ONLY` or `LITE_ONLY` and that UI's walkthrough. The header
shows the current time, so every regenerated image differs from the last
one in the clock at least. Only commit the ones whose screen actually
changed.

There's no backend, NFC reader or scale in the simulator. The real
`bambuddy_api.cpp` is wrapped in `#ifdef USE_ESP32`, and
`host/bambuddy_api_mock.cpp` is compiled in its place through the host YAML's
`esphome: includes:`. The mock fills the UI with demo printers, AMS units,
spools, storage locations and smart plugs, and applies UI actions locally.
Template buttons on the native API (`localhost:6053`) drive what the
hardware or the backend would:

- **NFC:** Simulate Linked Tag, Unlinked Tag (a plain NTAG), **Unknown
  Bambu Tag** and **Unknown OpenTag3D Tag** (unlinked tags carrying decoded
  spool data), Tag Removed, and **Location Tag** (the demo location
  "Shelf A").
- **AMS:** **AMS Insert** loads the pending spool into the first empty slot.
  **AMS Remove** takes the first assigned spool out, which stages it like a
  scan. **Assign Timeout** expires the 60 s assignment window.
- **Scale:** **Spool On Scale** (settling, then stable), **Empty Spool On
  Scale** (240 g, so Quick Weight triggers the archive prompt), **Scale
  Empty**, **Scale Offline**.
- **Printer:** **Plate Clear Request**.

The AMS, plate-clear and scale-offline buttons call `sim_*` methods that
exist only in host builds (`#ifdef USE_HOST` in `bambuddy_api.h`). Where the
mock stands in for a backend round trip (creating a spool from a tag, a
storage-location tag scan, archiving), it ends in the same state and status
message as the real component, so both UIs behave as on a device. The
class declaration in `bambuddy_api.h` is shared by both builds, so a new
public method on `BambuddyAPIComponent` that the UI calls also needs a stub
in the mock, or the host build fails to link.

Substitutions in the two host entry files take precedence over those from
packages. That's why `espoolbuddy_images` (the local image path) is set in
each entry file rather than in `host_common.yaml`, since `assets.yaml` would
otherwise override it.

`host/espoolbuddy_console_host_labels.yaml` is the simulator with a label
printer: Print Label writes the label to `label.pbm` in the current directory,
placed in an M220's 576-dot row as the console would print it. There's no
Bambuddy to draw labels, so the mock serves every spool the PNG named by the
`ESPOOLBUDDY_LABEL_PNG` environment variable (save one from Bambuddy's label
dialog as a 203 dpi black-and-white PNG):

```
ESPOOLBUDDY_LABEL_PNG=~/Downloads/label.png esphome run host/espoolbuddy_console_host_labels.yaml
```

**LVGL lists are static YAML by default.** Every list/grid in the UI (the
NFC spool picker, the printer picker, the AMS grid) is hand-unrolled in YAML
with a fixed cap and per-slot hide/show, since ESPHome's declarative LVGL
config has no "repeat N times" construct. The exceptions are the Storage
Locations screen (Settings) and the smart-plug popup (long-press or tap on
the quick-settings Power tile), whose rows are built and torn down at runtime
with raw LVGL C++ calls inside a `script:` lambda (`render_storage_locations`
and `render_plug_list` in `app.yaml`) — there's no reasonable static cap for
an externally-managed, unbounded list of locations or plugs. That pattern is
deliberately scoped to those two screens rather than adopted everywhere; see
the comment above `render_storage_locations` before reusing it elsewhere.
